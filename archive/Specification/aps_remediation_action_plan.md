## 1. 排序原则与泳道划分

### 1.1 为什么这么排（价值公式）

> **优先级 = 阻断风险 × 复用度 ÷ 返工成本**

| 排序 | 工作包 | 阻断风险 | 复用度 | 返工风险 | 结论 |
|---|---|---:|---:|---:|---|
| 1 | 模型语义修复 | 极高（计划不可执行） | 高（所有工厂共用） | 低 | **先做** |
| 2 | 独立校验器 | 极高（无法判断对错） | 高（所有工厂共用） | 中（会随规则变） | **紧随其后** |
| 3 | 规则参数外置 + 算子内核 | 高（每接一个工厂都要改代码） | 极高 | 中 | 第 5 周启动 |
| 4 | 分组与优先级 | 中（100 条线才痛） | 高 | 低 | 与 3 同批 |
| 5 | 数据模型实体化 | 中（多厂/多线才痛） | 极高 | 高（要迁移） | 第 9 周启动 |
| 6 | MRP | 中（原材判断缺失） | 高 | 中 | 第 11 周启动 |
| 7 | UI 重构 | 低 | 中 | 低 | 最后，随功能改 |

### 1.2 三条泳道

```
泳道 A（算法/求解）  ACT-01~08 ─► ACT-20~24 ─► ACT-32/34/35/36 ─► ACT-39
```

## 4. Phase 1：规则内核化（S3–S5，约 55 人日）

**目标**：把规则从代码搬到配置；工厂（甚至产线）可以自己定义软硬、权重、阈值、作用域；新增一个工厂 = 一份 Excel + 一份主数据，零代码。
**核心设计原则**（回应你的三点）：

1. **算法固定**：19 个算子（见 §6.2）的**函数签名与语义冻结**，随产品版本升级，不随工厂变化。
2. **规则是输入变量**：一条规则 = `算子 + 作用域 + 软硬 + 权重 + 分组 + 优先级 + 参数 + 生效期`。规则迭代 = 改 Excel 一行 + 重新求解，**不改代码**。
3. **权重必须进入计算**：组内归一化到"分钟当量"，组间用字典序（见 §6.4），并提供"权重敏感度报告"。

## 6. 关键设计（评审用）

### 6.1 开班决策与 95% 双层模型（D1 的落地）

**变量**

| 符号 | 含义 | 域 |
|---|---|---|
| `x[t,s]` | 任务 t 在班次 s 的批次数 | 0..per_shift |
| `o[l,s]` | 产线 l 在班次 s **是否开班**（决策） | {0,1} |
| `tail[l,s]` | 该班是否为该线的"收线尾班" | {0,1} |
| `load[l,s]` | 综合负荷 = 加工 + 换型 | 0..cap |

**约束**

```
load[l,s] = Σ_t x[t,s]·p_t + Σ_t started[t,s]·setup_t          # 换型入容量
load[l,s] <= cap[l,s] · o[l,s]                                  # 关班即零负荷
load[l,s] >= min_util · cap[l,s] · (o[l,s] - tail[l,s])         # 已开班必须 ≥95%
Σ_s tail[l,s] <= 1                                              # 每条线至多一个尾班
tail[l,s] <= o[l,s] ;  tail[l,s] <= 1 - o[l,s+1]                # 尾班只能是最后一个开班
```

**目标（在产能组内）**

```
min  Σ open_cost · o[l,s]          # 开班成本（防止"为了躲 95% 而多开班"）
   + Σ underload_penalty · gap[l,s] # 95% 缺口（软档时）
```

**两个 KPI（都必须上报表）**

| KPI | 公式 | 回答的问题 |
|---|---|---|
| 开班利用率 | `Σ load / (Σ o · cap)` | 开着的班，效率够不够？ |
| 日历覆盖率 | `Σ o / 日历班次数` | 该开的班，有没有开？ |

> **业务含义**：以前"跳班"能刷高 95%，现在"跳班"会拉低日历覆盖率，且开班本身有成本。两个指标互相制衡，KPI 才可被现场质疑。

### 6.4 分组与字典序（D1 + 权重生效）

```yaml
groups:
  - {id: G0_PHYSICAL,   priority: 0,  mode: hard}       # 模具/PM/ETA/批量/冻结
  - {id: G1_DELIVERY,   priority: 10, mode: lexicographic}
  - {id: G2_CAPACITY,   priority: 20, mode: lexicographic}
  - {id: G3_CHANGEOVER, priority: 30, mode: weighted}
  - {id: G4_INVENTORY,  priority: 40, mode: weighted}
```

求解：

```
for g in groups_sorted_by_priority:
    build_model(resolved_rules, bounds_from_previous_levels)
    minimize(objective[g])
    solve(level_budget)
    if infeasible:
        report_conflict(g)          # 定位到具体规则
        rollback_to_previous_level()
    bound[g] = ceil(value * (1 + slack[g]))   # slack 默认 0，可配 5%
    add_constraint(objective[g] <= bound[g])
```

**权重如何真正进入计算**：

1. 组内：`w_i / Σ_group w` 归一化，惩罚折算成**分钟当量**（缺口 ms→min、换型次数→min、拖期班次→min）；
2. 组间：字典序，**不跨组加权**，因此不存在"1 次换型 = 300,000 个班次"的量纲灾难；
3. 单条权重上限 50%，防止一条规则压死同组其他规则；
4. 提供**敏感度报告**（ACT-28）：权重 ±20% 的 KPI 变化表。

### 6.6 MRP 设计（D3 的落地）

**核心判断：MRP 不要塞进 CP-SAT，也不要另起一套"全量 MRP II"。**

你们的业务是"拉动式"：排程决定 FG/SF 什么时候做；MRP 只需要回答"往下推到原材料，够不够、什么时候到、影响谁"。

**边界（重要）**：

```
排程已确定的部分（FG/SF 的班次产出）  ──►  作为「固定供给」输入 MRP
未排程的下层（原材料/外购件）          ──►  MRP 做净需求 + 到货可行性
```

这样避免"MRP 重排半成品、排程又重排一次"的循环，也让容量决策仍然只由排程器负责。

**数据**：`part(type, lot_size, safety_stock_qty/days, scrap_rate, lead_time_days)`；`bom(parent, child, ratio, scrap_rate, level)`；`inventory_snapshot`；`purchase_order(eta, qty, qc_release)`。

**算法**：

1. 低层码（Low-Level Code）排序，从最深的一层往上算；
2. 按天分桶（近期可用班次桶做门控）；
3. 逐期净需求：
   ```
   gross[p,t]   = Σ_parent planned[parent,t] × ratio × (1 + scrap)
   avail[p,t]   = avail[p,t-1] + receipts[p,t] + planned[p,t] - gross[p,t]
   net[p,t]     = max(0, gross[p,t] + safety_stock[p,t] - (avail[p,t-1] + receipts[p,t]))
   planned[p,t] = ceil(net[p,t] / lot_size) × lot_size        # 或 lot-for-lot
   release[p, t - lead_time] += planned[p,t]
   ```
4. **Pegging**：每一条供给记录它满足了哪些需求（订单 + 数量），FIFO 分配；
5. **缺料**：`avail < 0` 的期 → 缺料量、受影响订单、最早可用日；
6. **回灌排程**：把每个任务的"最早可开工班次"写回 `material_ready_shift`，重新求解（最多 2 轮）。

**为什么先按天、不按工序**：

- 你们没有 process routine，SF 的工序不建模，提前期用一个数（生产 + 检验 + 周转）即可；
- 未来上了 routing，MRP 可以按工序级提前期展开，**接口不变**（`lead_time_days` → `lead_time_by_operation`）；
- 现在就把"料号级 MRP"做对，比"工序级但算不准"更有价值。

**输出（页面）**：

| 视图 | 内容 |
|---|---|
| 物料需求平衡表 | 每个料号 × 每天：毛需求/在途/计划订单/结存/覆盖天数 |
| 缺料预警 | 缺料料号、缺多少、影响哪些订单、最早可用日、建议动作 |
| Pegging 追溯 | 点一张订单，看到它由哪些供给满足、哪些还没着落 |

### 6.7 多厂/多线的分解边界

- **一个工厂一个模型**：`(site, family)` 一个求解任务；
- 跨厂只在"共享前道资源"时做顶层容量切片（本期不做，只留接口）；
- 100 条线不是"一个模型 100 条线"，而是"按产线组拆成 N 个模型 + 顶层协调"；
- 单模型目标变量数 ≤ 2 万；超过则自动降级（缩视区/分家族/固定部分变量）。

### 6.9 人力资源（Headcount）约束设计

> 背景：`Parameters-FG.csv` 有 `Headcount` 列（PGLINKAGE=3、PU07=12、PU22=12/15），`Parameters-SFN.csv` 有 `Head count`（1400T-6=1、轴套6 全空），但 `ProductParam` 无字段、`scheduler.py` 无变量、`validator.py` 无检查。详见诊断报告 §2.7 / G-63～G-66。

#### 6.9.1 资源模型的三个对象

| 对象 | 含义 | 来源 | 粒度 |
|---|---|---|---|
| **人员需求** `crew_req[line, part]` | 开这条线、做这个料号，一个班需要几人 | `Line-Staffing.csv`（缺省回落到产线级） | 产线 × 料号 |
| **人员供给** `H[site, date, shift]` | 这个班工厂实际能到岗几人 | `Labor-Availability.csv` | 站点 × 日 × 班 |
| **班组池** `pool[pool_id, lines, headcount]` | 哪几条线共用一个班组 | `Crew-Pool.csv` | 班组 |

**为什么需求要按料号而不是只按产线**：你们的 `PU22` 已经是 12/15 两种人数（不同产品人工含量不同）。按"当班在产料号取 max"来算，既尊重差异，又不会把同一条线上两个料号的人数相加（人不会因为换型翻倍）。

#### 6.9.2 模型（`labor_capacity` 算子，第 19 个）

沿用 §6.1 的 `o[l,s]`（开班决策），新增：

| 符号 | 含义 |
|---|---|
| `u[l,p,s] ∈ {0,1}` | 料号 p 在班次 s 于产线 l 上生产 |
| `crew[l,s] ∈ ℤ≥0` | 产线 l 在班次 s 的**在岗人数** |
| `co[l,s] ∈ {0,1}` | 班次 s 在产线 l 上是否发生换型 |
| `H[s]` | 该班可用人数（参数） |

约束：

```
# 1) 开班才有人，人数在 [crew_min, crew_max] 之间
crew[l,s] >= crew_min[l] · o[l,s]
crew[l,s] <= crew_max[l] · o[l,s]

# 2) 当班在产料号取最大人工需求（不是求和）
crew[l,s] >= crew_req[l,p] · u[l,p,s]          ∀ p

# 3) 换型需要额外人力峰值（技师/调机工）
crew[l,s] >= crew_base[l,s] + extra_co[l] · co[l,s]

# 4) 全厂同时开班人数不超过可用人数（核心硬约束）
Σ_l crew[l,s] <= H[s]

# 5) 共享班组：同一班组覆盖的产线，同时只能开 pool 允许的条数/人数
Σ_{l ∈ pool} crew[l,s] <= pool_headcount        ∀ s

# 6) 加班（可选，软）：先用人、后加班、加班有上限与成本
Σ_l crew[l,s] <= H[s] + OT[s] ;  OT[s] <= OT_max[s]
```

目标（新增 `G5_LABOR` 组，优先级排在 G4 之后）：

```
min  w_cost   · Σ crew[l,s] · shift_hours · hourly_rate
   + w_peak   · PeakHeadcount
   + w_smooth · Σ_s |Σ_l crew[l,s] - AvgHeadcount|
   + w_ot     · Σ_s OT[s] · overtime_rate
```

**注意"阶梯成本"**：人数是整数、且开班就得配齐一个班组，所以"半负荷开班"的人力成本与满负荷一样。这与 §6.1 的"开班成本 + 95% 下限"方向一致——**模型会自然倾向于"少而满"的班次**，而不是"多而空"。

```csv
# Labor-Availability.csv —— 供给侧（按天，允许覆盖）
Site,Date,Shift,Available Headcount,Note

Site,Line,Part No,Crew Required,Extra on Changeover,Skill Code,Effective From,Effective To

# Crew-Pool.csv —— 共享班组
Pool ID,Site,Lines,Headcount,Note
WL-POOL-1,WL,"PGLINKAGE, 轴套6",3,同一班组，同时只能开一条
```

**校验规则**（导入时强制执行）：

1. `Crew Required` 必须 > 0；缺值或空 → 报错（轴套6 当前就是空的）；
2. 同一 `(Site, Line, Part)` 在生效期内只能有一条规则；
3. `pool_headcount` ≤ 池内各线 `crew_req` 之和（否则约束无意义）；
4. `H[s]` ≤ 站点总人数；`H[s]` 为 0 时该班不允许开班；
5. `PU22` 的 12/15 必须显式配置两条料号级规则，不能用一条 `*` 掩盖。

### 12.2 术语表

| 术语 | 含义 |
|---|---|
| 算子（Operator） | 内核里一个固定的约束实现，有稳定的参数 Schema |
| 模板（Template） | 算子的对外声明（参数、作用域、默认软硬） |
| 规则实例（RuleInstance） | 某个工厂/产线对某个模板的一次具体配置 |
| 规则集（RuleSet） | 一组规则实例 + 分组 + 版本 |
| 解析后规则集（ResolvedRuleSet） | 完成继承/覆盖后的最终规则，落库 |
| 开班决策（Open decision） | 产线是否在某班次开工，是布尔决策变量 |

| 人员需求 / 人员供给 | 开线做某料号一个班需要几人 / 该班实际能到岗几人 |
| 班组池（Crew Pool） | 多条线共用的一组人，受同一人数上限约束 |
| 低层码（Low-Level Code） | BOM 中某物料出现的最深层次，MRP 自底向上计算的顺序 |
| Pegging | 供给与需求的对应关系，用于"缺料影响哪些订单" |
| 固定供给（Firm supply） | 排程已确定、MRP 不再重排的产出 |
