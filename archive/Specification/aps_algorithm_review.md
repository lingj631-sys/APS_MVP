# APS MVP 排产算法评审

**评审对象**：`src/scheduler.py` 的班次槽位 CP-SAT 模型，以及 `data_loader.py`、`shift_manager.py`、`prechecker.py`、`validator.py` 的配套逻辑。  
**复现数据**：`APS Database- Simulation draft.xlsx`，Site `WL`，2026-10-12 起 14 天；25 个生产任务、42 个班次。  
**结论**：架构方向正确（班次槽位 + 两阶段齐套 + 规则台账 + 独立校验），当前主要问题不在 CP-SAT 调参，而在**模型语义、度量口径、目标函数量纲**。其中若干项会直接产出“看起来 PASS、实际不可执行”的计划，建议先修。

## 2. P0：会产出“错计划”的问题

### 2.1 一个 MPQ 批超过一个班次 → 模型直接无解

`src/scheduler.py:357`：

```python
per_shift = max(1, min(task.lots, SHIFT_MS // task.lot_millis))
```

当 `lot_millis > SHIFT_MS` 时，`SHIFT_MS // lot_millis == 0`，`per_shift` 被抬成 1；但容量约束 `load <= SHIFT_MS` 又不允许这 1 个 lot 放进任何班次，于是 `sum(x) == task.lots` 无解。

实测 `WA14208S`（MPQ 72、CT 300s、TRP 0.71）一个 MPQ 批 = 8.45h。当前需求里它没有未覆盖需求，所以没触发；一旦有，整个排产直接失败。

**修法**：
- 把 `x[task, shift]` 从“lot 数”改为“件数/批量单位”，允许一个 MPQ 批跨多个班次；用一个 `batch_start/batch_end` 或“连续 active 段”表达“同一批跨班连续、中间不换线”。
- 或者保留 lot，但增加“批的剩余量”变量：`remaining[t, s] = remaining[t, s-1] + produced - lot_size`，允许 `produced < lot_size` 的跨班尾批。
- 同时修 `min_lots`：`min_lots = min(per_shift, mpq // lot_size)` 在 `per_shift < mpq` 时会把最小批量降到 `per_shift`（极端情况下是 1），等于允许 SF 每班只做很少件“滴灌”，同样违反 R-SF-07。

### 2.2 订单可被拆成不连续片段（R-FG-02 后半句未实现）

`src/scheduler.py:363-370` 只约束 `sum(x) == lots`，没有任何“同一任务的 active 班次必须连续”的约束；`runs` 只对“断了再开”收费一次，不禁止断。

60s 运行里 `FG::ORD_WL_WBC9317C_1022` 的实际分布：

```
10/14 中班 72, 10/14 晚班 72, 10/19 早班 72, 10/19 中班 72, 10/19 晚班 72, 10/20 早班 72
```

中间隔了 4 天多。这既违反“跨班连续、中间严禁换线”，也让导出的“制造开始时间/制造时间”看起来像 5.7 天的工单只干了 5.4h。

**修法（线性、便宜）**：对每个 task 加“无洞”约束：

```python
for s in range(lo, hi - 1):
    model.Add(active[t, s] + active[t, s + 2] <= 1 + active[t, s + 1])
```

如果 95% 填充导致硬约束不可行，就改成软惩罚（计 `hole` 数），但至少要让计划知道“这里断了一次”。

### 2.3 “换型次数”统计的是 task 连续块，不是真实换型

当前有两个口径混在一起：

- `src/scheduler.py:372-379` 的 `runs`：某个 task 从“不 active”变“active”算一次 run；同一班次里 3 个型号并存，只要它们上一班也 active，就不计新增 run。
- `src/main.py:112-126` 的 `_changeover_stats`：按 task 的 shift 集合数连续块，而不是按 `part_no` 聚合，也不含班内切换。

结果：报告“34 块”，但按班次统计，仅“班内型号切换”下限就是 61 次；实际换型次数（含班间切换）约 106 次。报告值比真实值低 3 倍左右。

更关键的是：**换型时间没有占用产能**。`src/scheduler.py:509-511` 的 `load` 只加 `x * lot_millis`，没有任何 setup 项。若每次换型 15 分钟，61 次 = 15.25h ≈ 2 个班次；当前 27 个班次只有约 5% 的余量（合计约 10.8h），装不下这 15.25h，至少要多 2 个班次或降低填充率。也就是说，“95% 利用率”是纯加工时间口径，计划在车间不可执行。

**修法**：
- 先定义清楚 R-FG-10 到底约束什么：单班并行型号数、单班换型次数、还是班间换型次数？三者模型不同。
- 若没有换型矩阵，至少加固定 `setup_minutes`，并复用现有 `p_act`：

```python
setup_ms = model.NewIntVar(0, SHIFT_MS, f"setup.{line}.{s}")
model.Add(setup_ms >= SETUP_MS * (sum(part_actives) - 1))
model.Add(load[s] + setup_ms <= SHIFT_MS)
```

- 若坚持“班次是原子、允许多型号”，就必须在目标函数里按真实切换次数计价，并在 KPI/导出里同时报告“型号块数”和“实际换型次数”，不能把两者混称“换型次数”。
- 若业务更看重可执行性，建议 MVP 先限制“每班最多 1 个型号”，把 95% 填充的粒度问题暴露出来，再决定是否允许多型号。

### 2.4 安全库存净需求公式错误

`src/data_loader.py:258-259`：

```python
usable = max(0.0, fg_avail[order.part_no] - param.target_stock)
net_need = order.demand_quantity - usable
```

当 `fg_avail < target_stock` 时，`usable=0`，`net_need=demand`；排产后的期末库存 = `avail + qty - demand`，仍可能低于目标。合成用例：需求 500、目标 100、期初 0、MPQ 48 → 排 528，期末 28 < 100。

正确口径应是“补足目标库存”：

```python
net_need = order.demand_quantity + param.target_stock - fg_avail[order.part_no]
net_need = max(0.0, net_need)
```

半成品的 `target_stock_days` 目前只打警告、按 0 处理，也应一并折算成件数。

### 2.5 分数 BOM 比例被取整

`src/scheduler.py:479`：

```python
ratio = int(round(component.bom_ratio))
```

Python 的 `round(0.5)` 是银行家舍入，结果 0；`round(1.5)` 是 2；`round(2.5)` 是 2。比例 0.5 时物料约束变成 `>= 0`，等于没有齐套约束；比例 1.5 时又要求 2 倍，过度约束。

**修法**：所有数量统一放大到整数标度（如 ×1000），用 `ratio_scaled = int(round(ratio * 1000))`，约束两边同乘 1000；或者用有理数 `Fraction` 生成整数系数。

### 2.6 非确定性

`src/scheduler.py:301-307` 设置 `num_workers=8`，`random_seed=1`。CP-SAT 在多 worker + 时间截止下不保证可复现；实测两次 30s 运行的目标值和计划都不同。

对排产系统，这不是“小问题”：计划员每天重跑一次，结果不同会直接摧毁信任；回归测试也无法断言。

**修法**：
- 最终计划用 `num_workers=1` + 固定 seed + 固定时间上限；或者先用 8 worker 探索，再用单 worker 从最优 hint 做一次确定性收拢。
- 记录 `plan_hash`、`solver_version`、`seed`、`time_limit`，输出“本次计划与上次差异”。
- 回归测试用单 worker。

### 2.7 期初库存日期与计划起点不一致

`src/main.py:37` 固定 `START_DT = 2026-10-12 07:00`，但 `Initial Stock` 表头是 `Initial Stock(10/13)`，客户需求也从 10/13 开始。

实测：`WBC9317C` 10/13 需求 960，期初 0，排产 1008；单班最多 8 lot = 576 件，至少需要 2 个班次（这次运行用了 10/12 中、10/12 晚、10/13 早 3 个班次）。如果快照口径是 10/13 07:00、10/12 不可用，这单**无法准时**；当前 100% 准时依赖 10/12 这一天。

需要确认：
- 10/12 是可用生产日，且期初库存快照不含 10/12 产出？
- 还是期初库存已含 10/12 产出，计划不应再从 10/12 起算？

两者只能选一个，否则会双重计算或隐藏延误。

### 2.8 日历决策与预检未接线

`src/main.py:71-80` 计算了 `cal_mode`（实测 `FIVE_TWO`），但第 80 行固定：

```python
active_mode = CalendarMode.SEVEN_ZERO
```

README 说“按负荷比自动推荐并绑定日历模式”，实际没有绑定。

同样，`src/main.py:67-68` 只打印预检报告，没有 `raise` 或阻断。README 第 54 行说“发生绝对超载时抛出 `CAPACITY_OVERLOAD_EXCEPTION`”，代码里没有这个异常抛出；`precheck.has_exception` 也没有被使用。

**修法**：
- 用 `cal_mode` 生成日历；按 `4/3 → 5/2 → 7/0` 做“日历升级阶梯”：先用推荐模式求解，若交期不可行再升一级，并在报告里写明“因交期压力从 5/2 升级到 7/0”。
- 预检异常时：输出《交期调整建议表》并阻断，或显式 `--force` 才继续；不要静默进入求解。

## 3. P1：计划“不合理”的问题

### 3.1 95% 可以靠“跳班”满足，空闲没有成本

`src/scheduler.py:532-550` 只对 `running=1` 的班次算缺口；空班次 `running=0`，不进入 `gap`/`below`。`src/validator.py:60-82` 也只统计 `loads` 里出现的班次。

结果：PGLINKAGE 在 10/15 早/中班直接不生产，避开 95% 检查；按开工班次算 95%+，按日历算只有 61.2%。这不是“高利用率”，是“把空闲藏起来”。

**修法**：
- 对“产线开工区间内的空洞”加惩罚或硬约束：

```python
hole = model.NewBoolVar(...)
model.Add(hole >= run[s-1] + run[s+1] - 1 - run[s])
```

- 尾班豁免改成“每个 campaign 的最后一个班次”，而不是“整条产线最后一个班次”；否则一条线只开 1 个班次时，1% 利用率也会 PASS。
- 报告里同时给“开工班次利用率”和“日历班次利用率”，并列出空洞原因（缺料/无需求/为凑 95%）。

### 3.2 没有 JIT/库存目标，95% 把未来需求提前拉

目标函数只有 `sum(end_of)`（完成班次），没有 `start_of`，也没有库存/提前期成本。95% 填充需要把每个班次凑满，于是把 10/17、10/20 的需求拉到 10/12–10/14 生产。

实测 WCA1894 提前 4.7 天、WBC9317_1020 在 60s 运行里提前 5.9 天。对成品来说，这就是库存；R-FG-07“月末 ≤2 天安全库存”没有进入模型。

**修法**：
- 加 `start_of[t]`，并给 FG 一个“不早于 `due - EARLY_WINDOW`”的窗口（例如 2 天 = 6 个班次），允许软违反并计价；或者直接加库存持有成本 `sum(inv[p,s])`。
- SF 用 `lead_time_days` 约束：`start_of[sf] + lead_shifts <= start_of[parent]`。
- 把“提前生产”作为报告项（提前天数/库存占用），不要只报“准时率”。

### 3.3 目标函数量纲不一致、权重失衡

`src/scheduler.py:47-55`：

```python
FG_COMPLETION_WEIGHT = 1
CHANGEOVER_WEIGHT = 300_000
CONCURRENCY_WEIGHT = 50_000
```

`end_of` 的单位是“班次索引”，`runs` 的单位是“次”。一次换型 = 300,000 个班次，完成时间项完全被淹没。注释说“worth 300 seconds of shift time”，但 300 秒相对 8h 班次应该约 `0.01`，不是 `300,000`——差了约 7 个数量级。

同理，`CONCURRENCY_WEIGHT=50_000` 与换型 `300_000` 的 6:1 比例也没有业务依据；规则表里两者权重都是 0.10。

**修法**：
- 要么把所有项换算成同一单位（秒/小时/元），用真实成本系数；要么做**字典序分层**：交付 → 利用率 → 换型 → 库存 → 稳定 → 日历偏好，每层用上界固定后求下一层。
- 至少不要把“班次索引”和“换型次数”直接相加；当前权重会让模型为了省 1 次换型接受任意程度的提前生产/碎片化。

### 3.4 先到先停 + 压缩是时间盒

`src/scheduler.py:254`：填充层一旦找到“所有非尾班 ≥95%”的解就 `StopSearch()`，不再优化完成时间/并行型号。真正的换型集中靠 `_compact()`（`src/scheduler.py:166-203`）在剩余预算里再解一次。

后果：
- 计划质量取决于剩余预算：60s 运行 27 块，30s 运行 34 块。
- 如果压缩层没时间或失败，就保留填充层的碎片计划。
- `_compact` 的 hard 95% 档即使块数比当前多也会被接受（`if mode == "soft" and grouped >= blocks` 只对 soft 档检查），因为它认为 95% 优先；但当前计划可能已经是 0 缺口，此时 hard 档的唯一价值是优化换型，如果它返回更差的块数就没有理由接受。

**修法**：
- hard 档也加“不劣于当前计划”的接受条件（至少 `grouped <= blocks`，或按 `block` 与 `on_time` 的字典序比较）；不要把“95% 硬”当成自动接受的理由。
- 更好的做法：一次字典序求解，先固定交付，再固定缺口上界，再最小化真实换型；不要用“先到先停”当优化器。
- 给填充层一个可证明的下界（例如最少开工班次数），达到下界再停，而不是“第一个干净解”。

### 3.5 R-FG-10 是软约束，且语义与规则不一致

`src/scheduler.py:404-425` 的并行型号惩罚是软约束；`CONCURRENCY_WEIGHT=50_000` 远小于换型 `300_000`，所以模型可以为了少一次换型接受第 4 个型号同班。

规则 R-FG-10 写的是“单班换型次数 ≤3”，代码校验的是“单班并行型号数 ≤3”（`src/validator.py:203-224`）。这两者不等价：3 个型号是 2 次换型；A→B→A 是 2 个型号但 2 次换型。当前模型没有班内顺序，无法表达 A→B→A。

**修法**：
- 先和业务确认度量：并行型号数、班内换型次数、班间换型次数。
- 如果是硬上限（工装/模具数），直接 `model.Add(sum(part_actives) <= 3)`。
- 如果保留软约束，权重必须高于换型，否则永远被换型买掉。

### 3.6 订单级 task 阻碍同料号合并与库存共享

`src/data_loader.py:276-332` 为每个客户订单行创建一个 FG task，并为每个 FG task 创建独立的 SF task。同一个料号的多个订单（如 WBC9317C 有 4 单、WBC9317 有 2 单）无法合并生产，也无法用后一单的库存补前一单。

后果：
- 同料号被拆成多个生产块，换型/碎片增加。
- 库存不能在订单间共享；`stock_covered` 只是把“前一任务的余量”记到后一任务，且默认第 0 班次就有（2.4 的变体）。
- 无法做“按料号备库、按订单分配”的常规 APS 逻辑。

**修法（建议下一轮架构）**：把决策变量从“订单任务”改成“料号 × 班次产量”，用**料号级库存平衡**：

```text
inv[p, s] = inv[p, s-1] + prod[p, s] - consume[p, s]
inv[p, s] >= 0
cum_prod[p, s] + opening[p] >= cum_demand[p, s]   # 每个交期
```

FG 的 `consume` 就是发货需求；SF 的 `consume` 是下游 FG 产量 × BOM 比例。这样：
- 同料号自动合并，库存自动共享；
- 不需要 `stock_covered` 的时间错位假设；
- 订单分配变成排产后的 FIFO/EDD 后处理，不影响机器排程；
- 变量数从“订单行 × 班次”降到“料号 × 班次”，规模更小。

这是比“修约束”更大的改动，但它同时解决 2.4、2.5、3.6、3.2 的一半问题，建议作为 MVP 下一阶段的主线。

### 3.7 换型时间/顺序依赖未建模

即使不看 2.3 的统计口径，`load` 里没有 setup，`per_shift` 也没有给 setup 留余量。数据里没有换型矩阵，至少需要固定换型时间；否则“95%”只是加工时间，不是班次时间。

**修法**：
- 主数据加 `Changeover_Minutes`（默认 15/30 分钟）或 N×N 矩阵。
- 用 `load[s] + setup[s] <= SHIFT_MS`，并明确 95% 的分母是“纯加工”还是“含换型”。
- 若做顺序依赖，用 `circuit`/`NoOverlap` 或班内小 TSP；MVP 可以先固定值。

### 3.8 主数据字段被忽略

`src/data_loader.py:207-213` 读取了 `Scrap rate`、`生产提前期(days)`、`No. of hours/shift`、`No. of shift/day`，但调度侧从未使用：

- SF `Scrap rate=3%`：23,435 件半成品对应约 703 件报废，当前计划没有补。
- SF `生产提前期=1 day`：当前只要求 SF 在 FG 前 1 个班次（8h），实测间隔约 8–15h，不足 1 天。
- `hours_per_shift`/`shifts_per_day`：`shift_manager.py` 全局写死 8h/3 班，多班制/短线会错。

**修法**：要么在净需求和约束里使用（推荐），要么在加载时明确打警告并写入“未生效字段”清单，不能静默忽略。

## 4. 目标模型建议

### 4.1 建议的目标层级（字典序）

1. **L0 可行性**：产能（含换型）、料号级库存平衡、MPQ/最小批量、批次连续、并行型号硬上限、日历可用性、释放日/交期窗。
2. **L1 交付**：FG 不晚于交期；不可行时最小化加权拖期（客户优先级/订单权重）。
3. **L2 产能**：最小化开工班次数/产线空洞；95% 作为“每 campaign 非尾班 ≥95%”的软目标，缺口数有上限。
4. **L3 换型**：最小化真实换型次数（顺序相关则用矩阵）。
5. **L4 库存/JIT**：最小化提前生产天数/库存积分。
6. **L5 稳定性**：最小化与冻结计划/上次计划的偏差。
7. **L6 日历偏好**：需求允许时优先周末停机。

实现方式：逐层求解并固定上一层上界（`model.Add(prev_obj <= best)`），而不是把不同量纲的项乘一个大数相加。若坚持加权，所有项先换算成“秒”或“元”，并用可证明的 big-M。

### 4.2 关键约束写法

```python
# 1) 批次/任务连续，不留洞
for s in range(lo, hi - 1):
    model.Add(active[t, s] + active[t, s + 2] <= 1 + active[t, s + 1])

# 2) 换型时间占产能
setup_ms = model.NewIntVar(0, SHIFT_MS, f"setup.{line}.{s}")
model.Add(setup_ms >= SETUP_MS * (sum(part_actives[line][s]) - 1))
model.Add(load[line, s] + setup_ms <= SHIFT_MS)

# 3) 产线空洞惩罚 / 禁止
model.Add(hole[line, s] >= run[line, s - 1] + run[line, s + 1] - 1 - run[line, s])

# 4) 不早于窗口（FG）
model.Add(start_of[t] >= due_shift[t] - EARLY_WINDOW_SHIFTS)

# 5) 料号级库存平衡
model.Add(inv[p, s] == inv[p, s - 1] + prod[p, s] - consume[p, s])
model.Add(inv[p, s] >= 0)
```

| 路径 | 内容 | 工作量 | 适用 |
|---|---|---|---|
| A. 小改 | 保留订单 task；补 2.1–2.8、3.1–3.5、3.7 | 1–2 周 | 先让现有 MVP 的计划“可执行、可复现” |

## 6. 需要业务确认的 6 个问题

1. **95% 的分母**：是纯加工时间，还是含换型/停机的班次时间？尾班豁免是“整条线最后一个班次”还是“每个 campaign 最后一个班次”？

3. **提前生产**：成品允许提前几天生产？是否用 `Target Stock(days)` 作为上限？R-FG-07 的“2 天”是默认值还是硬上限？
4. **批次跨班**：一个 MPQ 批必须连续跨班，还是允许中间插入其他型号？最小连续段是多少？
5. **快照口径**：`Initial Stock(10/13)` 与计划起点 10/12 的关系？10/12 的产能是否可用？
6. **交付粒度**：所有需求按 15:00 早班截单是否准确？是否允许部分交付/按日分批发货？

## 7. 附：校验器的独立性问题

`validator.py` 的 9 项检查里，有两项是“同义反复”：

- `_check_conservation`（`src/validator.py:85-102`）：`task.quantity` 是从 `plan` 复制的，`sum(shift_breakdown)` 是从同一个 `x` 提取的，所以“排产量等于净需求且班次产出守恒”几乎必然 PASS；它没有回到 Excel 重新计算净需求。
- `_check_stock_balance`（`src/validator.py:163-177`）：`closing = fg_avail[pn]`，而 `expected = opening + produced - consumed` 是用同一套累加算出来的，恒等；只有 `closing >= target_stock` 这一半有独立意义（也正好能抓到 2.4）。

因此“9/9 PASS”不等于“30 条规则全部实现”。`format_rule_compliance_matrix`（`src/validator.py:246-275`）对绑定到检查项的规则直接用检查结果，可能出现“规则状态是 `BLOCKED_DATA`/`UNIMPLEMENTED`，但矩阵显示 PASS”的情况（例如 R-SF-06/R-FG-07 绑定到库存检查）。建议：
- 区分“当前计划满足”与“规则已实现”（两个维度）。
- 对未实现/数据缺失的规则固定显示 `TODO`/`N.A.`，不允许被一个 PASS 的检查覆盖。
- 增加数据级独立复核：从 Excel 重新读 CT/TRP/MPQ/库存/需求，重新算净需求和工时，而不是复用 loader 的中间结果。

## 8. 附：性能与规模化

- 当前 25 任务/42 班次，60s 预算下 44.2s；30s 预算下约 15s。规模翻 10 倍（250 任务/多产线）时，变量和约束近似线性增长，但 CP-SAT 搜索可能超线性。
- 建议：
  - 按产线分解（产线之间只通过共享 SF/库存耦合，可用料号级库存平衡解耦）。
  - 按周滚动，近期精排、远期粗排。
  - 贪心/EDD+FFD 生成初始解作为 hint，替代当前 6% 预算的 CP-SAT hint。
  - 对称破除：同料号任务按 due 排序、同班次内的任务固定顺序。
  - 只在最终收拢阶段开单 worker，探索阶段多 worker。
