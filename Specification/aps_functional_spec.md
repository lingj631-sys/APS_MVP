# 自研智能排产系统 Functional Specification

**版本**：0.2 草案  
**日期**：2026-10-03  
**状态**：基于当前对话整理，未确认项见第 11 章  
**文档目的**：作为自研 APS MVP 的业务功能规格草案，用于与物流专家、计划员、IT/算法团队对齐范围、功能边界和验收标准。

**0.2 变更内容**：新增 4.5 问题规模与数据画像、4.6 需求来源与订单形态、5.2.1–5.2.2 排产规则能力边界；同步补充第 10、11 章相关行动项与待确认问题。

## 1. 背景与目标

### 1.1 背景

公司为制造型企业，生产模式为流程型、批量生产，分为半成品和成品。当前日计划由物流计划员通过 Excel 手工排产，具体到每条产线。现有方式存在以下痛点：

- 过度依赖个人经验，尤其是资深排产同事的经验。
- 客户订单变更频繁，导致需要反复重新排产。
- 排产质量和效率受人员能力、状态、经验影响大。
- 希望将资深排产专家的知识沉淀为可配置规则和高级算法，降低对个别专家的依赖。

### 1.2 项目目标

开发一套适合自身工厂的智能排产系统，复杂度尽量低、功能适当，避免百万级通用 APS 的高投入和强定制化。

MVP 目标：

- 针对单一产品进行排产，示例产品为“挂杆”。
- 覆盖成品和半成品。
- 生成日计划，具体到每条产线。
- 排产建议在质量和运算效率上优于现有物流同事的人工排产结论。
- 支持业务规则可配置、人工可确认、异常可重排。
- 不追求绝对最优解，100% 接受次优解。

## 2. 项目范围与 MVP 边界

### 2.1 MVP 包含范围

| 维度 | MVP 范围 |
|---|---|
| 产品 | 单一产品，例如雨刮器中的“挂杆” |
| 层级 | 成品和半成品 |
| 计划层级 | 日计划 |
| 计划对象 | 具体到每条产线 |
| 排产顺序 | 按物流经验，先排成品，再排半成品 |
| 用户 | 物流计划员作为普通操作用户；物流专家作为业务规则和算法知识来源 |
| 数据 | SAP、客户 Web EDI，订单数量、BOM 等；支持手工维护 |
| 需求来源 | 以已释放、具交付约束力的客户订单为主输入；预测量是否进入排产待确认，见 4.6 |
| 输出 | 排产建议、产线级日计划、方案评估 |
| 异常 | 订单变更、缺料、设备故障等波动下的重排 |
| 求解策略 | 接受次优解，设置时间上限，优先可行解和业务满意度 |

### 2.2 MVP 不包含或暂不展开

以下内容当前对话中未确认纳入 MVP，建议明确排除或后续扩展：

- 全厂全产品、全工序 APS。
- 采购计划、配送计划、仓储作业计划。
- MES 执行控制、设备控制。
- 财务成本核算、详细成本优化。
- 多工厂、跨工厂协同。
- 外协、模具、人员、能源等复杂约束，除非物流专家确认必须纳入。
- 通用规则引擎与自定义规则表达式；跨期累计类规则（见 5.2.1 的 R7、R8）。

## 3. 术语与角色

| 术语 | 说明 |
|---|---|
| APS | 高级计划与排程系统 |
| 物流同事 | 普通用户，将来操作排产系统的人 |
| 物流专家 | 公司内资深排产同事，业务规则和排产经验来源 |
| 挂杆 | MVP 示例产品 |
| 成品 | 最终交付产品 |
| 半成品 | 成品生产过程中的中间产品 |
| 硬约束 | 绝对不能违反的约束 |
| 软约束 | 可以权衡、尽量满足的约束 |
| 次优解 | 不追求数学最优，但满足业务要求、优于人工排产的可行解 |
| 释放单 | 客户已确认、具交付约束力的订单数量与时间，排产的主要输入 |
| 预测量 / 框架量 | 客户给出的预期需求量，会滚动修订，不等同于确定订单 |
| 时界 | 需求由可变更转为锁定的时间边界，常见划分为预测区、确认区、冻结区 |
| 滚动窗口排产 | 近期精细排产、远期粗略排产，逐期向前滚动的排产方式 |

## 4. 业务现状与排产场景

### 4.1 生产模式

- 流程型生产。
- 批量生产。
- 分半成品和成品。
- 多种产品、多条产线，但 MVP 只聚焦单一产品“挂杆”。

### 4.2 当前排产方式

- 物流计划员使用 Excel 手工排产。
- 日计划，具体到每条产线。
- 排产强依赖个人经验。
- 客户订单变更频繁，导致频繁重排。

### 4.3 已知排产约束

当前已识别但未完全确认的约束包括：

- 产线产能。
- 瓶颈工位。
- 工作日历，包括中秋、国庆等公司特定休息日、换休。
- 库存。
- 其他约束需与物流同事继续沟通。

### 4.4 排产目标

- 准时交付排第一，不可妥协。
- 其他目标排序待物流专家确认。
- 可能包括换型最少、产能利用率、库存最低、成本最低、负载均衡等。

### 4.5 问题规模与数据画像

**为什么必须先量化**：求解器选型（6.1）、算力配置（6.2）、是否需要问题分解和滚动窗口、验收 POC 用什么样的数据集，全部取决于问题规模。当前文档只提到"小样本准确率高、大样本耗时指数增长"，但没有定义"大样本"在本工厂的具体数值，因此该风险目前无法评估，也无法证伪。

**规模指标清单（待填）**：

| 指标 | 典型值 | 峰值/最差值 | 数据来源 | 状态 |
|---|---|---|---|---|
| 单次排产的计划跨度（自然日数） | 待填 | 待填 | 现有 Excel 模板 | 待确认 |
| 排产频率（每天/每周几次） | 待填 | 待填 | 计划员访谈 | 待确认 |

| 参与排产的产线数量 | 待填 | 待填 | 主数据 | 待确认 |
| 挂杆成品物料号 / SKU 数量 | 待填 | 待填 | SAP 物料主数据 | 待确认 |

| 班次结构与换休复杂度 | 待填 | 待填 | 考勤/工作日历 | 待确认 |

**规模对模型复杂度的影响（用于快速判断可行性）**：

排产模型的决策变量规模近似为：

```
变量规模 ≈ 订单行数 × 可选产线数 × 时间槽数
约束规模 ≈ 变量规模 × 参与约束的种类数
```

示例（数值仅为说明公式，非本工厂数据）：若 200 订单行 × 4 产线 × 计划跨度 7 天 × 每天 2 班次 = 11,200 个基础 0-1 变量；再叠加换型顺序变量（同产线两两组合）后通常会上升一个数量级。这个量级对 CP-SAT / 混合整数规划属于可求解范围；若订单行数上升 5–10 倍，则必须依赖问题分解、滚动窗口和启发式，纯精确求解不可行。

**工程结论**：

- 求解器 POC（第 10 章第 8 项）必须使用峰值规模的数据集，不能用几十行样本验证性能。
- 若量化后规模确实很小（例如订单行 < 50），应重新评估是否需要求解器，简单规则 + 启发式可能就够了，避免过度建设。
- 若规模很大，应在 MVP 阶段就引入滚动窗口排产（只精排近期，远期粗排），而非一次性排全部。

### 4.6 需求来源与订单形态

5.1 只写了"客户订单数量"，但排产系统的输入是"确定要交付的量"还是"客户预期量"，会直接决定模型是否有可行解、以及计划是否会频繁推翻重来。制造企业的客户需求通常不是单一形态：

| 需求来源 | 确认程度 | 典型形态 | 是否参与排产 | 处理策略 |
|---|---|---|---|---|
| 客户 EDI 释放单 / 召唤单 | 高，具交付约束力 | 按日/按周确定数量与交货时间 | 是，主要输入 | 直接排产，准时交付为硬约束 |
| 客户预测 / 框架量（Forecast） | 低，会滚动修订 | 未来数周至数月，量与时点均可能变 | 待确认 | 建议不直接排产，转为安全库存目标 |
| 内部预测 / 补货需求 | 中 | 库存低于水位触发 | 待确认 | 走库存策略，不进入订单排产 |
| 样品 / 试制 / 紧急插单 | 高但不稳定 | 临时插入 | 待确认 | 走重排流程，见 5.6 |

**MVP 倾向（待物流专家确认，见 11.7）**：

- 只对已释放、有交付约束力的需求做订单级排产。
- 预测量不直接生成生产任务，而是通过安全库存 / 备货策略间接影响半成品计划。
- 理由：预测一旦直接进入排产，"准时交付率第一"这个目标就失去明确定义（排的是未确认的量），同时每次预测滚动修订都会触发大范围重排，与"客户订单变更频繁导致反复重排"的现有痛点叠加，系统会变得不可用。

**需一并确认的订单形态细节**：

- 交付模式：JIT 直送产线 / 入客户仓 / VMI，影响交货时间窗口的严格程度。
- 时间窗：客户是否给出精确到货时段，还是仅"当日到达"即可；是否有最早/最晚到货约束。
- 最小交付包装：整箱 / 整托 / 看板单元，决定批量能否自由合并拆分。
- 订单可变性：释放后是否允许调整数量、能否拆分交付、是否有最大日/周供货量上限。
- 时界划分：客户侧是否存在冻结期（预测区、确认区、冻结区），边界是几天。
- 需求优先级依据：按交货日期、客户等级，还是订单紧急度标记。

## 5. 功能需求

### 5.1 数据集成与主数据管理

系统应支持：

- 从 SAP 获取订单、BOM、库存等数据。
- 从客户 Web EDI 获取客户订单数量等数据。
- 区分需求来源类型（释放单、预测量、内部补货、插单），并按 4.6 的约定决定是否进入排产。
- 支持手工维护和修正关键数据。
- 管理以下主数据：
  - 产品、成品、半成品。
  - BOM 和物料关系。
  - 产线、瓶颈工位。
  - 产线产能。
  - 工作日历、休息日、换休。
  - 库存，包括成品库存、半成品库存、在制品。
  - 换型/切换时间矩阵，若业务需要。
  - 排产规则和目标优先级。
- 支持数据版本和生效日期。
- 提供数据校验和异常提示。

### 5.2 排产规则与约束配置

系统应支持：

- 配置硬约束和软约束。
- 配置约束优先级。
- 配置排产目标及权重。
- 明确“准时交付第一”为最高优先级目标。
- 规则可版本化、可追溯、可由物流专家维护。
- 支持规则试算和影响分析。

> 具体硬约束、软约束、优先级和目标排序待物流专家确认，见第 11 章。

#### 5.2.1 规则能力边界（MVP 支持的规则类别）

"规则可配置"如果不划定表达能力边界，就会变成无上限的开发需求：物流专家提出的每一条经验都会被理解为"要做一个配置项"。因此先约定 MVP 只支持 R1–R6 六类规则，R7、R8 明确排除；无法归入下列类别的规则一律走变更评审并归入后续版本。

| 类别 | 说明 | 示例 | MVP 支持度 |
|---|---|---|---|
| R1 排序 / 优先级规则 | 同类任务之间的先后次序依据 | 交货日期近的优先；紧急插单优先；客户等级高的优先 | 支持 |
| R2 分配限制规则 | 哪些任务允许落到哪些资源 | 某半成品只能在 A 线生产；订单-产线兼容性；新旧产线能力差异 | 支持 |
| R3 容量与时间规则 | 资源可用时间与任务时长 | 工作日历、休息日/换休、班次时长、设备维保窗口、任务准备/清理时间 | 支持 |
| R4 批量规则 | 生产批量的下限、上限与拆分合并 | 最小生产批量、最大单批量、同订单/同物料合并、订单拆分许可 | 支持 |
| R5 顺序依赖规则 | 相邻任务的顺序相关成本或禁止组合 | 换型时间矩阵、颜色由浅到深、清洗顺序、禁止连续生产的组合 | 有条件支持：需矩阵化数据，否则降级为固定换型时间 |
| R6 分层联动 / 齐套规则 | 上下游层级之间的时间与数量耦合 | 成品不得早于对应半成品完成；半成品齐套提前期 | 支持范围待确认，见 5.4 与 11.2 |
| R7 跨期累计规则 | 跨天/跨周的数量上下限 | 客户周累计配额、月最大供货量、库存水位置换 | 不支持（后续版本） |
| R8 稀缺资源竞争规则 | 共享非产线资源的分配 | 模具数量与切换、人员技能与班次、能源限额、外协产能 | 不支持，与 2.2 排除项一致 |

**表达形式的约定**：

- 规则以"参数 + 有限取值 + 模板化条件"的形式配置，MVP 不引入通用规则引擎或规则脚本语言（不内嵌 Drools、不开放自定义表达式）。
- 每条规则必须能落到上述模型的某个具体结构（变量上界、约束系数、目标函数权重、可行性白名单之一），否则不予实现。
- 新增规则类别需要同时明确其在模型中的表达方式与对求解时间的影响，经评审后才能进入范围。
- 规则必须带生效日期与版本，可回滚（与 5.1 数据版本要求一致）。

#### 5.2.2 规则冲突与降级策略

- 硬约束优先于一切软约束和目标，不可违反。
- 同类软约束之间按配置优先级顺序裁决；优先级相同时由目标权重决定。
- 当硬约束集合本身无解时，不做静默放宽：返回冲突诊断，列出参与冲突的硬约束、涉及订单与资源，并给出可放宽项建议，由计划员确认后重排（与 5.3、5.6 一致）。
- 规则命中多条时的默认策略：取最严格的一条生效，并在结果解释中标明生效规则，避免"规则叠加后无人能解释结果"。
- 规则数量本身会影响求解时间，需要对单产品启用规则条数设上限并监控（与 4.5 规模指标一并评估）。

### 5.3 排产引擎

系统应支持：

- 输入客户订单、库存、产线产能、日历、约束、目标。
- 输出日计划，具体到每条产线。
- 覆盖成品和半成品。
- 默认先排成品，再排半成品。
- 支持设置求解时间上限。
- 在时间上限内返回最佳可行解或次优解。
- 不追求绝对最优解，100% 接受次优解。
- 当无可行解时，给出冲突诊断和放宽建议。
- 支持多方案生成和对比。
- 支持人工确认后发布排产结果。

### 5.4 成品与半成品联动

系统应支持：

- 按物流经验先排成品，再排半成品。
- 半成品排产结果可反向影响成品计划。
- 支持成品和半成品的库存、产能、齐套关系参与计算。
- 支持分层排产和联动排产两种模式，具体采用哪种待确认。
- 支持锁定的成品计划对半成品计划形成约束。

### 5.5 排产结果展示与交互

系统应提供：

- 产线级甘特图或排产视图。
- 订单视图、产线视图、产品视图。
- 产线负荷、瓶颈工位负荷。
- 库存和齐套情况。
- 排产结果解释，例如为什么某订单排在该产线、该时段。
- 人工调整功能，例如拖拽、锁定、冻结、局部修改。
- 调整后重新校验约束和 KPI。
- 方案对比视图，包括与人工排产基准的对比。

### 5.6 重排与异常处理

系统应支持：

- 订单变更触发重排。
- 缺料触发重排。
- 设备故障触发重排。
- 其他异常触发重排。
- 支持全量重排和局部重排。
- 支持计划冻结期和锁定规则。
- 支持人工确认后再重排。
- 记录重排原因、前后差异、影响范围。
- 保留审计日志。

### 5.7 方案评估与知识沉淀

系统应支持：

- 统计和评估以下 KPI：
  - 准时交付率。
  - 排产耗时。
  - 换型次数或换型时间。
  - 产线利用率。
  - 瓶颈工位利用率。
  - 库存和在制品水平。
  - 人工干预次数。
- 与物流同事人工排产结果进行对比。
- 将物流专家的经验转化为规则、参数、权重、案例。
- 建立规则库、案例库、参数版本。
- 支持专家对排产结果进行标注和反馈。

### 5.8 权限、审计与集成

系统应支持：

- 用户角色和权限管理。
- 普通用户：物流计划员。
- 专家用户：物流专家。
- 管理员：IT/算法/系统维护。
- 操作审计和版本记录。
- 与 SAP、客户 Web EDI 集成。
- 预留与 MES、WMS、PLM、QMS 等系统的接口能力。
- 支持 API、中间表、文件导入导出等方式。

## 6. 非功能需求

### 6.1 性能与求解策略

已确认原则：

- 100% 接受次优解。
- 不追求绝对最优解。
- 优先在可接受时间内给出满足硬约束、业务满意的可行解。
- 求解器可能使用 OR-Tools，也可能使用其他求解器，需根据实际情况再探讨。
- 已知现象：OR-Tools 等求解器在小样本时准确率较高，大样本时耗时可能呈指数级增长。

建议采用的工程策略：

- 设置求解时间上限。
- 问题分解，例如先成品再半成品。
- 启发式算法与精确求解器混合。
- 优化模型本身，减少变量和约束复杂度。
- 支持多线程并行搜索。
- 支持多方案并行计算。
- 当时间上限到达时，返回当前最佳可行解。
- 当无可行解时，返回冲突诊断。

**前置依赖**：本节所有策略参数（时间上限、是否分解、是否需要滚动窗口）都无法在 4.5 问题规模量化之前确定。POC 与压测必须使用 4.5 中记录的峰值规模数据集，而非小样本。

### 6.2 算力与部署

- 长期可能部署在云端，例如阿里云。
- 可租用算力，按需平衡算力与需求。
- 可考虑按量付费、抢占式实例、弹性伸缩。
- 可采用“基础算力 + 弹性算力”的混合架构。
- MVP 阶段初步参考配置：8 核 16GB，但需压测确认。
- 排产任务通常无状态、可容错，适合抢占式实例。
- 需评估 SLA、成本、任务频率、数据安全。

### 6.3 可解释性、可配置性、可扩展性

- 排产结果应可解释。
- 业务规则不应写死在代码中。
- 支持未来扩展到多产品、多产线、多工厂。
- 支持未来接入更多约束和系统。
- 支持算法替换和求解器替换。

### 6.4 安全与可靠性

- 保护 SAP、客户 EDI 等业务数据。
- 支持权限隔离。
- 支持操作审计。
- 支持故障恢复和任务重试。
- 支持数据备份。

## 7. 验收标准

MVP 验收建议包括：

### 7.1 功能验收

- 能生成单一产品“挂杆”的日计划。
- 覆盖成品和半成品。
- 计划具体到每条产线。
- 支持先排成品、再排半成品。
- 支持规则配置和人工调整。
- 支持订单变更后的重排。
- 支持排产结果展示和导出。

### 7.2 质量验收

- 排产建议质量优于现有物流同事人工排产结论。
- 准时交付率不低于人工排产，或达到约定目标。
- 换型、产能利用率、库存等指标不劣于人工基准。
- 需定义基准数据集、对比方法和量化指标。

### 7.3 效率验收

- 排产运算时间在可接受范围内。
- 具体时间上限待定，例如 5 分钟、10 分钟或 15 分钟。
- 支持设置时间上限，超时返回次优解。

### 7.4 业务验收

- 物流计划员可独立操作。
- 物流专家认可规则和结果。
- 系统不依赖个别专家经验即可运行。
- 专家经验已沉淀为规则、参数或算法。

## 9. 风险

| 风险 | 说明 |
|---|---|
| 规则不明确 | 硬约束、软约束、优先级未完全确认 |
| 数据质量 | SAP、EDI、手工维护数据可能不完整或不实时 |
| 求解器性能 | 大样本可能耗时过长 |
| 问题规模未量化 | 4.5 缺失时，求解可行性、算力配置和 POC 结论均不可信 |
| 预测混入排产 | 未确认量进入排产会扭曲准时交付目标，并与频繁重排叠加导致系统不可用 |
| 规则范围失控 | 5.2.1 能力边界不确立，"规则可配置"会演变为无上限开发需求 |
| 算力成本 | 云端算力需求与成本需平衡 |
| 人工基准难获取 | 没有历史人工排产数据，难以证明“优于人工” |
| 范围蔓延 | 从单产品扩展到全厂全产品 |
| 专家依赖转算法难 | 专家经验难以完全规则化 |
| 验收标准模糊 | “优于人工”需要量化和基准 |
